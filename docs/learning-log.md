# Learning log

One entry per phase. Format: concept · traced example · my exercise · what I can now explain.

## Phase 0 — environment and contract

- **Concept:** guard-rails are the design system. Before a single component exists, the repo already enforces: no raw units/colours/`!important` in CSS (stylelint), no inline styles and jsx-a11y strict (ESLint), every story is an axe test that fails CI (`a11y.test: 'error'`), strict TypeScript, public API only through `src/index.ts`.
- **Traced example:** the first draft of `reset.css` contained a `prefers-reduced-motion` block with `0.01ms !important`. stylelint rejected it. The fix was not an exception — it was moving reduced-motion into the token layer (duration tokens → 0), exactly as `TOKENS.md` already said. The tool caught a rule the human had just broken.
- **Negative test:** an `<img>` without `alt` injected into the Welcome story made `vitest --project storybook` fail with `image-alt`. A green test suite that cannot go red proves nothing; now we know this one can.
- **Exercise (run by the AI at the author's request, 2026-10-15):** add `<a href="#">Детальніше</a>` to the Welcome story and expect axe to fail. **It did not fail — 1/1 passed.** The AI's prediction was wrong: axe's `link-name` rule only checks that a link *has* an accessible name; "Детальніше" ("Read more") is a name. Whether the name describes the link's *purpose* (WCAG 2.4.4 Link Purpose) is not something axe, or any automated tool, can judge. The fix is still the same — link text that works out of context ("Детальніше про дизайн-систему" / "Read the design-system principles") — but it has to come from a human review step, not the test suite. This is the first entry for the case study's "an AI output I corrected" section: the AI's own exercise premise was wrong, the tool proved it, and the lesson is why `CONTRIBUTING.md` requires a manual pass alongside axe.
- **Understanding question — why `px` is allowed only on `outline*`, `border*`, `scroll-*`:** these three are *structural* widths that must stay visually constant: a 2 px focus ring or 1 px border should not scale with the user's font size (a 0.125rem ring at 200 % zoom becomes a 4 px blob; a hairline border becomes blurry). `scroll-margin`/`scroll-padding` offset the focused element from sticky headers (2.4.11 Focus Not Obscured) and are tied to the header's px height. Everything else — spacing, type, radius — goes through tokens so it scales and themes. If `outline` had no px exception, the only lint-clean options would be `outline: none` (forbidden by `declaration-property-value-disallowed-list`) or a `rem` ring that distorts under zoom; in practice people reach for `outline: none` and the focus indicator disappears — the single most common keyboard-accessibility failure on the web. The exception exists so the right thing is also the easy thing.

## Phase 1 — tokens → CSS → Button

- **Concept:** a token is a named decision. `color.action.primary.bg` is one name with **six** values (light `#1D4FD7`, dark `#4D84FA`, hc-light `#122F84`, hc-dark `#80A8FF`, linen `#2B3FBF`, linen-dark `#8FA0FF`). The Button never knows the hex; it reads `var(--iz-color-action-primary-bg)`. Themes are override files that re-alias semantic tokens; components don't change.
- **Traced example — one token, six links, end to end.** Run `npm run build:tokens` first; every line below is checkable.

  | # | Layer | Where | What it says |
  |---|---|---|---|
  | 1 | primitive | `tokens/primitives/color.linen.json` | `color.ultramarine.600` = `#2B3FBF` (tagged `H` — exact handoff value) |
  | 2 | semantic (base) | `tokens/semantic/color.json` | `color.action.primary.bg` = `{color.blue.600}` |
  | 3 | theme override | `tokens/themes/linen.json` | `color.action.primary.bg` = `{color.ultramarine.600}` |
  | 4 | registry | `tokens/themes.config.ts` | `linen` → attribute `linen`, colourScheme `light`, contrast `AA` |
  | 5 | generated CSS | `src/styles/design-tokens.css` | `[data-theme='linen'], [data-iz-theme='linen'] { --iz-color-action-primary-bg: #2B3FBF }` |
  | 5b | alias layer | same file, `:root` | `--iz-color-bg-accent: var(--iz-color-action-primary-bg)` — the handoff's name, following the canonical one into every theme |
  | 6 | component | `Button.module.css` | `.primary { --iz-button-bg: var(--iz-color-action-primary-bg) }` |
  | 7 | rendered | Storybook *Actions/Button/Primary*, Theme toolbar → `linen` | the toolbar is generated from `themes.config.ts` and sets both attributes |
  | 8 | Figma | `Semantic/color/action/primary/bg`, mode `linen` → alias `color/ultramarine/600` | **live since 2026-10-25** — imported by `tools/figma-plugin/` (ADR-018/020); 116 × 6 modes, 696 aliases, matched the dry run exactly |

  All eight links are live. Link 8 is still the only one that is not automatic — Git is canonical and Figma is a mirror (ADR-004) — but "re-entered by hand" became "re-run the plugin after a build". What the plugin's own history taught: the two failed runs were both on the human step (the wrong menu item, a similarly named file), and the fix that worked was not a clearer instruction but baking the data into the plugin so there was no file to pick (ADR-020).
- **Things the tools caught this phase (all mine):** (1) `tokens:validate` — two semantic tokens aliased themselves because they shared a name with a primitive (ADR-007). (2) `check:contrast` — `text.muted` on `surface.raised` was 4.44:1, invisible to the eye, 0.06 below AA; fixed by darkening `neutral.500`, not by lowering the bar. (3) stylelint — raw `px`/`em` in the first CSS; resolved with one documented utility and one scoped exception. (4) axe in the story test — **pending state had no accessible name**: `visibility: hidden` on the label (to keep the width stable) removed it from the accessibility tree; fixed with `opacity: 0`. (5) The spec said `aria-busy`; React Aria actually uses `aria-disabled` + `data-pending` — spec corrected to reality, not the other way round. (6) React Aria does not dispatch a native `click` on keyboard activation, so the Playwright click counter was wrong; activation is asserted in the Storybook interaction test instead.
- **Reviewed token change demo (run 2026-10-23, both halves).** One primitive edited, `color.ultramarine.600`.

  *Half one — the change that should be rejected.* `#2B3FBF` → `#6B7BE0` (a lighter ultramarine, visually plausible). `npm test` went red with the pairs named: six failures, **all in linen only**, lowest 3.01:1 — `fg.on-accent` on the accent dropped to 3.79:1, `text.link` on the page to 3.48:1, `fg.on-accent-subtle` on the tint to 3.01:1. The other five themes stayed green, which is the proof that the primitive is linen-scoped. A reviewer sees the exact pairs and the exact deficit, not "contrast failed".

  *Half two — the change that passes.* `#2B3FBF` → `#2A3DB8` (a half-step darker). Updated with no hand-editing: `src/styles/design-tokens.css` (5 declarations — `action-primary-bg`, `action-primary-fg`, `border-focus`, `text-link`, `status-info-border` — one primitive, five semantic roles), `dist/css/linen.css`, `dist/ts/tokens.d.ts`, `dist/figma/tokens.json`, `docs/specs/tokens.dtcg.json`, and every Storybook story through the Theme toolbar. Token **names** did not change, so no component, spec or test needed touching. Manual step, still: `Primitives/color/ultramarine/600` in Figma.

- **What this demo caught — a silent bug in the build I had just written.** With the accent changed, `--iz-color-action-primary-bg` was correct in linen but `--iz-color-bg-accent` — the handoff's name for the same decision — was still base blue `#1D4FD7` in *every* theme. Cause: theme blocks only re-declare the tokens that theme overrides, and the alias layer is not overridden by any theme, so a resolved literal on `:root` froze the base value. Two pairs of eyes would not have found this; a changed colour did. Fix (ADR-014): an alias-layer token is emitted as `var(--iz-canonical)`, never as a resolved literal, so it follows its target by construction and the whole class of bug disappears rather than being tested for. Verified across all six themes: `--iz-color-bg-accent` now resolves to the same hex as `--iz-color-action-primary-bg` everywhere.

## Phase 2 — primitives for Today (TextField first)

- **Concept:** the spec is written before the code and is the review artefact; the code only maps props to structure and styles, behaviour comes from React Aria. For a field that means: the *box* is the target (border, background, focus ring), the error element exists before it is shown, and the field never owns Enter or Escape — the pattern does.
- **Things the tools caught this phase (all mine, 2026-10-25):** (1) `tsc` with `exactOptionalPropertyTypes` + `noUncheckedIndexedAccess` — `placeholder` and `styles.input` can be `undefined`, and React Aria's `Input` refuses that; guarded the same way Button does. (2) The unit test for "error element exists before it is shown" failed because React Aria's default `validationBehavior="native"` does not render the empty error slot until the browser reports an error — and sets the native `required` attribute, whose bubble would compete with our message. Switched to `validationBehavior="aria"` and wrote it into the spec (ADR-022). (3) The computed accessible description is `"Numbers only. "` with a trailing space, *because* the empty error element is already referenced — the contract causes the whitespace; assistive tech collapses it, so the test matches a regex, not the component changing. (4) Playwright: whichever test navigated first in a run failed with "element(s) not found" — Vite's cold compile on macOS 12 outruns the 5 s default expect timeout. Fixed in `playwright.config.ts` (15 s), not per test.
- **Decision this phase forced:** ADR-021 — a 40 px desktop control height (`size.target.lg`) and Button `md` moving from 32 to 40, so a field and its button in the quick-add row are the same height. Decided before the CSS was written, not inside it.
- **Checkbox (2026-10-26) — things the tools caught, all mine:** (1) React Aria Components 1.22's `CheckboxField` does **not** associate a `<Label>` placed inside it with the input — no `id`, no `aria-labelledby` — so every story went red on axe's `label` rule and the unit test could not find a checkbox by name. The fix is hand-wiring with `useId` (ADR-023); the "clicking the text toggles" test is what proves both links. (2) `aria-checked="mixed"` is not an attribute: React Aria sets the native `indeterminate` *property* and the browser reports mixed — the right matcher is `toBePartiallyChecked()`. (3) `defaultSelected` on a `rerender` of a mounted uncontrolled component does nothing (defaults apply at mount), so read-only gets its own `render`. And one scoping decision from the handoff: the ActionRow done ring is a `<button>` with Undo, not a checkbox — so Checkbox stayed a plain form control instead of growing a "circle" variant nobody would use.
- **Chip (2026-10-26).** A naming collision the handoff did not see: `UBIQUITOUS-LANGUAGE.md` split *Tag (static)* from *Chip (removable, interactive)*, while the product calls property, stage and filter pills all "Chip" and has nothing removable. Settled as one `Chip` whose `variant` decides the element (ADR-025); the vocabulary now has an `emphasis` axis (quiet / tint / strong) because the handoff's stage colours are weight, not status — and the product rule is one accent per screen. Two tokens had to exist first: a 28 px `size.target.sm` and a 12 px `font.caption` role (ADR-024); without them Chip would have reached past the tier rule for a primitive. **Things the tools caught, all mine:** (1) `tsc` — `args.onChange` cannot be typed on a discriminated union of props (it exists only on the filter branch); the story keeps its own spy instead. (2) Playwright — a story with a `play()` runs it **on load** in the iframe, so the first Tab from Playwright lands *after* the play's Tab; e2e drives a play-less story (`StaticThenFilter`). (3) The spacing exception in 2.5.8 is the only reason a 28 px chip is acceptable — so the spec puts the ≥ 8 px gap on the *pattern*, where it can be enforced.
- **Card (2026-10-26).** The simplest component so far, and the one with the most rules *against* things: never clickable as a whole, no shadow, no margin, no media query. Its value is what it refuses to do — each refusal is a layout or a11y failure avoided downstream. The triage card's 14 px needed a canonical token (`radius.xl`, ADR-026) rather than the alias name. **Things the tools caught, all mine:** (1) ESLint `no-restricted-syntax` — a stray `style={undefined}` in a story; the rule has no tolerance for an inline `style` attribute even when empty, which is right. (2) stylelint `selector-class-pattern` — `.padding-md` / `.radius-xl` are kebab, CSS-Modules classes must be camelCase; the TSX maps prop values to class names explicitly instead of string-building them. (3) `tsc` — a polymorphic `as` tag makes JSX intersect the ref types of every allowed element; typed the tag as `'div'` with a comment, since every prop we pass is shared by all four. (4) Playwright — `locator('article, div').filter({ hasText }).first()` resolved to Storybook's root wrapper, so the "1 px border" read `0px`; the card is now found as *the parent of its heading*. (5) Playwright — pressing Tab straight after `goto` lands on nothing because the story has not mounted; wait for the article first (Button's e2e already did this, I had skipped it). The `LinenSeparation` story exists for the human check the Phase 1 review asked for: six white cards on the warm page with a 1.21:1 edge — judge it in the Theme toolbar before trusting "no shadow".
- **Toast (2026-10-26) — the last of the five for Today, and the first with time in it.** Two gaps surfaced *before* the spec could be honest: the token pipeline could not say "a translucent shadow, dropped in dark mode" (no alpha, no `shadow` type — ADR-027), and React Aria's Toast is `UNSTABLE` with an `alertdialog` per toast and a FIFO queue, the opposite of the handoff's polite, replacing `status` (ADR-028). **Things the tools caught, all mine:** (1) React Compiler lint — writing `onCloseRef.current` during render, and `setState` inside an effect to reset the pause; replaced with an effect-written ref and the documented "previous prop" pattern. (2) jsx-a11y, three times in a row — every handler I hung on the `role="region"` landmark (keyboard, then pointer, then focus) was refused, and each refusal moved the handler to a *better* place: Escape and focus-pause now live on the two buttons, the only things that can hold focus; pointer-pause is an imperative listener, because resting a pointer on a toast is not an interaction with the landmark. The rule did not just block code, it drew the right boundary. (3) Playwright — a hidden `role="status"` is excluded from role queries; the e2e asks for it with `includeHidden` to prove the live region stays mounted while closed. (4) `tsc` — React Aria's Button types `onBlur` on `Element`, not `HTMLButtonElement`. (5) Two lessons about my own gates: `npm run check | grep …` hides the exit code — a red `check:specs` and four red unit tests sailed past it until I gated on `$?`; and user-event hangs under fake timers (it awaits `setTimeout` internally even with `delay: null`), so timer tests drive the exact DOM events the component listens to with `fireEvent`, which is also the more honest test of a listener.
- **Menu (2026-10-26) — the first overlay, and the one React Aria does almost entirely.** Roving focus, wrap, type-ahead, Escape, focus return, `aria-haspopup` / `aria-expanded`, `menuitemradio` + `aria-checked` — all from `MenuTrigger` + `Popover` + `Menu`; our code maps props to structure and adds two things the library leaves to us: an inset focus ring on the item (the hover background alone is ~1.1:1) and a reserved tick column in single-selection mode. Decisions: the split button is a *composition* owned by ActionRow (two buttons, two names, one visual group); the popover body uses Card-raised tokens without being a Card (menu inset is 8 px, Card offers 16 / 24). **Caught — three were my assertions, not the component:** (1) React Aria emits `aria-haspopup="true"`, ARIA's boolean form of a menu; I had hard-coded `"menu"` in a test, a story and the spec. (2) `onAction` is called as `(key, null)` — a strict `toHaveBeenLastCalledWith('+3d')` fails on the extra argument. (3) Focus returns to the trigger *after* the popover unmounts — asynchronous, so the assertion needs `waitFor`. A probe test that printed the real DOM and call args settled all three in one run, where reasoning had stalled. **(4) The one that was not my assertion:** an e2e for "Tab closes the menu" failed in a real browser, and a browser probe showed Tab and Shift+Tab do nothing inside the open menu — React Aria's popover is modal for assistive technology and contains focus, and the library warns against `isNonModal` outside combobox-style components. The repo's own rule said "Tab out closes" for *non-modal* popovers; a menu is not one. Spec, e2e, MDX and `ACCESSIBILITY.md` now say what the component does (ADR-029). A test that fails for the right reason is worth more than one that passes for the wrong one.
- **Modal (2026-10-26) — the blocking overlay, and the one the product uses least.** The handoff's rule is "confirm nothing, Undo instead", so the spec starts by saying when *not* to open one. React Aria does the hard parts — hides the page from assistive technology, locks scroll, traps and restores focus — and the unit test proves each (the outside button leaves the accessibility tree while the dialog is open). Named `Modal`, not `Dialog`: the vocabulary says Dialog is the role. **Caught — two were React Aria facts the repo had wrong, the rest mine:** (1) React Aria does **not** set `aria-modal`; it hides everything outside with `aria-hidden`, because AT support for `aria-modal` is inconsistent — test, spec and `ACCESSIBILITY.md` said `aria-modal="true"`; they now say what happens and why. (2) React Aria focuses the *dialog element* on open, while the repo rule and APG (least-destructive action first — Cancel) want the first control; the component moves focus on, dialog as the fallback — and the first attempt did nothing because a child's effect runs *before* the ancestor's focus effect, so the move is deferred one macrotask. (3) `check:specs` wanted a `focus` state, then the ring's two tokens; `jsx-a11y/no-autofocus` flagged a redundant `autoFocus` in a story. (4) The e2e drove the `Keyboard` story, whose `play()` had already opened the dialog on load — the Chip lesson again; e2e now drives a play-less `Default`. (5) A stray escape in a one-line Python `print` silently skipped a patch and I re-ran failing tests on unchanged code — read the tool's first line of output, every time.
