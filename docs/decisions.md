# Decisions (ADR log)

Format: problem · options · decision · reason · consequence · revisit when.

## ADR-001 — Single package with `agent/` inside, not a monorepo
Problem: ODL ships three packages; we want the MCP/spec layer but minimal infrastructure.
Options: (a) npm-workspaces monorepo like ODL; (b) one package with `agent/` folder shipped in the tarball.
Decision: (b).
Reason: learning and portfolio scope; one lockfile, one build, one version. The agent code is small.
Consequence: the MCP server is installed with the library (`node node_modules/@iz/design-system/agent/server.mjs`). If a web-component package is ever added, we migrate to workspaces then.
Revisit when: a second runtime package is needed.

## ADR-002 — React Aria Components for every interactive component
Problem: native HTML + a headless lib only for complex widgets vs one behaviour library everywhere.
Options: (a) native elements for Button/TextField/Checkbox, React Aria for Dialog/Tabs/Select; (b) React Aria for everything.
Decision: (b).
Reason: one consistent API (`onPress`, `isDisabled`, `data-*` state attributes) across all components; mobile screen-reader and press handling are already solved; the learning goal includes reading how a strict APG implementation works.
Consequence: a hard runtime dependency (`react-aria-components`), documented as a peer dependency; slightly larger bundle; we must not re-implement behaviour on top.
Revisit when: bundle size becomes a constraint, or a component's native semantics are strictly better (e.g. native `<select>` on mobile — then wrap, don't replace).

## ADR-003 — Four themes in v1 scope
Problem: light+dark is enough for the demo; hc themes double contrast work.
Options: (a) light + dark; (b) light, dark, hc-light, hc-dark.
Decision: (b), built in that order; light must be complete before dark starts.
Reason: the high-contrast themes are the strongest accessibility evidence for the portfolio and force the semantic layer to be done properly.
Consequence: every component is checked in four themes; `check:contrast` runs AAA thresholds on hc themes.
Revisit when: time runs out — hc themes can be cut to "documented, partially implemented" without touching components.

## ADR-004 — Token sync direction: Git → Figma, with Figma exports reviewed as PRs
Problem: both tools can hold tokens; bidirectional sync drifts.
Decision: `tokens/*.json` in Git is canonical. Figma variables are imported/re-entered from it. Changes made in Figma are exported to `tokens/figma-export/`, diffed by `tokens:sync`, and applied to the source by a reviewed commit.
Consequence: a Figma-originated change is never "live" until merged.

## ADR-005 — Target size
Decision: WCAG 2.2 AA minimum is 24 × 24 CSS px (2.5.8); `size="lg"` is 44 px as a recommended touch target. Documentation never calls 44 px the AA minimum.

## ADR-006 — A ~120-line custom token transformer instead of Style Dictionary (for now)
Problem: DTCG 2025.10 became stable in Oct 2025 with object-valued colours (`{colorSpace, components, hex}`) and dimensions (`{value, unit}`); Style Dictionary 5 reads DTCG but its handling of these object shapes and of per-theme output needed custom transforms/formats anyway.
Options: (a) Style Dictionary 5 + custom transforms; (b) a small readable script (`scripts/lib/dtcg.mjs` + `tokens-build.mjs`) that resolves aliases and emits CSS, types and a resolved DTCG snapshot.
Decision: (b). `style-dictionary` stays installed as a devDependency for a later comparison but is not on the build path.
Reason: the learning goal is to understand the pipeline, and the whole pipeline is now five small functions (flatten → resolve → cssName → toCss → write). Output is one CSS file with four theme blocks, OS bridges and reduced-motion, plus `tokens.d.ts` and `tokens.dtcg.json` for Figma/MCP/Claude Design. The source stays pure DTCG, so Style Dictionary or Terrazzo can replace the script without touching `tokens/*.json`.
Consequence: no Android/iOS outputs until needed; `tokens:validate` is our own (aliases, cycles, shapes, tier rules, theme-only-overrides-semantic).
Revisit when: a second platform output is needed, or Style Dictionary gains first-class DTCG 2025.10 colour/dimension support.

## ADR-007 — Name-collision rule between tiers
Problem: `tokens:validate` caught `radius.full` and `easing.standard` aliasing themselves — the semantic token had the same path as the primitive.
Decision: primitive groups that could share a name with a semantic role get a distinct suffix (`radius-scale.*`, `curve.*`). Semantic names describe roles (`radius.md`), primitives describe scales (`radius-scale.2`).
Consequence: the validator's cycle check is the enforcement; this ADR is the explanation future-us will look for.

## ADR-008 — Linen theme: handoff values are exact; the gaps are derived and listed
Problem: `specs/HANDOFF.md` § *Linen theme tokens* gives 19 colour roles with Light/Dark values and measured ratios. The scaffold's semantic layer has 46 colour roles, so ~27 have no handoff value — and themes may only alias primitives, so every linen colour needs a primitive first.
Options: (a) only override the 19 roles the handoff names, and let the rest fall back to the base (blue/neutral) palette — a linen page with Tailwind-blue status tints; (b) derive the missing values from the handoff's own hues and record each one.
Decision: (b). `tokens/primitives/color.linen.json` carries the palette; every entry is tagged `H` (exact handoff value) or `D` (derived) in its `$description`.
Derived (`D`), and why: status tints `crimson.100/900`, `jade.100/900`, `ochre.100/900` (the handoff gives one status colour per state, not a bg/fg/border triple); `crimson.400/500` and `crimson.700/800` (hover/active steps for the danger button, which the handoff's `-hover` half-step / `-active` two-step rule implies but does not tabulate); `jade.800`, `ochre.700` (a status *fg* on its own tint needs more contrast than the same hue on the page, where the handoff measured 4.9 and 5.3); `text.muted` and `text.disabled` (the handoff has two text levels, the scaffold has four).
Consequence: no derived value ships unchecked — `check:contrast` runs every pair in the linen themes too. The `H`/`D` tags make a later design review a filter, not a re-read.
Rejected: (a) — it would put `#2563EB` status borders on a linen page and quietly break "one accent per screen".

## ADR-009 — Handoff token names are mapped with an alias layer, not renamed
Problem: `specs/HANDOFF.md` specifies `--iz-{category}-{role}-{emphasis}-{state}` (`--iz-color-bg-accent`, `--iz-space-400`). `docs/TOKENS.md` specifies `category.concept.property.variant.state` (`--iz-color-action-primary-bg`, `--iz-space-inset-md`). Both are already written against: the handoff's nine pattern specs use the first, the existing `Button.module.css` and four themes use the second.
Options: (a) rename the scaffold to the handoff scheme (breaks Button, four themes, `tokens.d.ts`, `docs/TOKENS.md`, package exports); (b) keep the scaffold and record the mapping in prose only (the handoff's pattern code would not compile); (c) keep the scaffold as canonical and emit the handoff names as an alias layer.
Decision: (c), per the review call on 2026-10-23. Canonical names stay the source of truth; `tokens/semantic/*.handoff.json` and `color.pairs.json` alias them. One override point per role: a theme overrides the canonical token and the alias follows.
Enforced by `tokens:validate`: only `*.pairs.json` / `*.handoff.json` may alias semantic → semantic, and a theme may never override an alias-layer token (it would fork the pair).
Three handoff names cannot be emitted verbatim, because the DTCG path is already a group and a path cannot be both a group and a token:

| Handoff | Emitted as | Why |
| --- | --- | --- |
| `--iz-color-text` | `--iz-color-text-primary` | `color.text` is a group (`primary`, `secondary`, `muted`, …) |
| `--iz-color-border` | `--iz-color-border-default` | `color.border` is a group (`default`, `strong`, `focus`, `danger`) |
| `--iz-color-brand` | `--iz-color-brand-bg` | `color.brand` is a group, so the mark colour gets its on-pair |
| `--iz-color-status-success` / `-warning` | `--iz-color-text-success` / `-warning` | `color.status.success` is already a bg/fg/border group; `--iz-color-status-critical` maps to `--iz-color-text-danger` for symmetry |
| `--iz-font-body` (composite) | `--iz-font-body-size`, `-line-height`, `-weight`, `-family` | a CSS custom property cannot be partially consumed; the scaffold's per-property pattern is kept |

Consequence: `--iz-color-bg-accent` and `--iz-color-action-primary-bg` are both real and always equal. A codemod to one scheme stays possible; see the governance row in the handoff's system-areas table.

## ADR-010 — The handoff's type/space/radius/motion live in the base semantic layer, not in the linen theme
Problem: the handoff's Type, Space, Radius and Motion tables give one value each, not a Light/Dark pair — only the colour table has two columns.
Decision: those roles go into the base semantic layer (`scale.handoff.json`, new type roles in `typography.json`); `linen.json` / `linen.dark.json` override colour, plus the three type roles that collide with the base Inter scale (`font.body`, `font.label`, `font.heading`).
Reason: the scaffold's theme model is "themes re-alias colour roles"; forcing non-colour tokens through a theme file would mean every future theme has to restate the space scale.
Consequence: `--iz-space-400` = 16 px in every theme. Line-height stays a unitless number (`line-height.147` = 1.4667 for the handoff's 15/22) rather than a px `leading.*` dimension, so a theme override never changes a token's `$type`.
Not tokenised: `--iz-motion-spring-settle` (stiffness 260 / damping 18 / mass 1). DTCG has no spring type; it is a motion-library config, so it stays in the motion spec for Phase 2. Letter-spacing needed a new dimension unit — `em` is now accepted by `tokens:validate` alongside `px`/`rem`.

## ADR-011 — `tokens/themes.config.ts` is the theme registry, and themes may extend each other
Problem: the theme list was hardcoded in three places (`THEMES` in `scripts/lib/dtcg.mjs`, the theme blocks in `tokens-build.mjs`, the `hc-` prefix test in the contrast script). The handoff also asks for `themes.config.ts` and for `linen.dark` to be an override of `linen`, not of the base.
Decision: one typed registry, `tokens/themes.config.ts`, holding id, attribute, file, `extends`, `colorScheme`, `contrast` target and OS bridge. `scripts/lib/dtcg.mjs` imports it with a plain `import` — Node 22.23 strips the types, so there is no build step and the same file is the app's type source. `loadTheme` applies every override file in the extends chain, outermost ancestor first.
Consequence: adding a theme is one entry; validate, build and contrast pick it up with no other edit. `linen.dark.json` holds colour only (47 roles) and inherits linen's type from its parent. `tokens-build.mjs` emits, per theme, exactly the tokens that theme's chain overrides — which is why linen can override type where the older themes override only colour.
Attribute: the generated CSS carries **both** `[data-theme='x']` (docs/TOKENS.md, already used by Storybook's toolbar) and `[data-iz-theme='x']` (the handoff's `<html data-iz-theme="linen">`). Two selectors on one rule costs nothing and neither spec has to move. The OS bridges require that neither attribute is set.

## ADR-012 — Contrast coverage is derived from the on-pair rule, and it is a test
Problem: a hand-written pair list silently stops covering the system the moment someone adds a background role.
Decision: `tokens/contrast-pairs.json` has two sections — `pairs` (combinations no convention implies: text levels, borders, the focus ring) and `onPairs` (each `color.fg.on-*` token and the background roles it partners). `scripts/check-contrast.ts` fails if any background role (`color.surface.*`, `*.bg`, `*.bg-*`, excluding the alias layer) has no `onPairs` entry, or if an `fg.on-*` token is listed nowhere. Thresholds come from each theme's `contrast` field. `kind: 'exempt'` is reported but never fails — WCAG exempts disabled controls.
Consequence: 288 graded pairs across 6 themes (+6 exempt). Adding a background without its foreground fails `npm test`, verified with a throwaway `color.action.tertiary.bg`.
Wired into `npm test` as `src/test/contrast.test.ts` (one assertion per theme) rather than as a shell step, so a failure names the theme and prints the offending pairs next to the component tests. `npm run check:contrast` stays as the CLI.
**The focus ring is checked against surfaces only.** Adding `border.focus` on `action.primary.bg` failed at 1.00:1 in linen and hc-light — the ring and the accent are the same token by design. The handoff specifies a 2 px outline with a 2 px *offset*, so a band of surface always separates ring and component and there is no ring/component adjacency to measure. The pair is removed with that reasoning recorded in `contrast-pairs.json`; if a ring is ever drawn flush on a component, it comes back and the ring needs a contrasting inner halo.

## ADR-013 — `iz/no-raw-colors` and `iz/no-raw-spacing` as a local ESLint plugin; CSS stays with stylelint
Problem: the handoff's rule 4 is "a hex or px in app code fails the build", and ESLint cannot see inside `.css` files without an extra language plugin.
Decision: `tools/eslint-plugin-iz/` (two rules, no dependencies) covers TS/TSX by reading every string and template literal — so `style={{ color: '#ff0000' }}`, a tagged template and a stray `'16px'` prop default are all caught. `.stylelintrc.json` already covers CSS with `color-no-hex`, `color-named: never`, `function-disallowed-list` and `unit-disallowed-list`; that division is kept rather than adding `@eslint/css`.
Exempt paths: `tokens/`, `scripts/`, `tools/`, `*.test.*`, `*.e2e.ts`, `*.stories.tsx`, config files — the places where a raw value is the subject rather than a mistake.
Consequence: `npx eslint` on a file containing `color: '#ff0000'` errors; so does `npx stylelint` on a `.css` file containing `color: #ff0000`. No existing file in the repo trips either rule.

## ADR-014 — The CSS alias layer is emitted as `var(--iz-canonical)`, never as a resolved value
Problem: `tokens-build.mjs` writes, per theme, only the tokens that theme's chain overrides — correct for an override file, wrong for the alias layer. An alias-layer token (`--iz-color-bg-accent`, `--iz-color-fg-on-accent`, `--iz-color-text-subtle`) is overridden by no theme, so a resolved literal on `:root` froze the base value: in linen, `--iz-color-action-primary-bg` was `#2B3FBF` while `--iz-color-bg-accent` was still base blue `#1D4FD7`. Silent — the variable existed and held a plausible colour.
Found by the reviewed-token-change demo (docs/learning-log.md, Phase 1), not by a test.
Options: (a) include, in each theme block, every alias-layer token whose target that theme overrides; (b) emit alias-layer tokens as `var(--iz-<canonical>)`.
Decision: (b). Declared once on `:root`, the alias follows its target into every theme the way custom properties are meant to — and `dist/css/<theme>.css`, which emits every token, stays self-consistent because the canonical sits in the same block.
Consequence: no code path can emit a literal for an alias-layer token, so the bug class is gone by construction rather than guarded by a test. Verified: `--iz-color-bg-accent` resolves to the same hex as `--iz-color-action-primary-bg` in all six themes.
Rejected: (a) — it would have worked, and would have had to be re-derived correctly for every future theme and every new alias.

## ADR-015 — Figma export carries collections and modes in `$extensions`
Problem: `dist/figma/tokens.json` put collection and mode metadata in top-level keys, while specs/HANDOFF.md asks for `$extensions`, and a plain top-level key makes the file something neither a DTCG reader nor a Figma plugin can be pointed at.
Decision: one vendor key, `$extensions["design.iz.figma"]`, holds `format`, the two collections, their modes and the default mode; each Semantic token carries `$extensions["design.iz.figma"].modes.<mode>` with the `alias` to enter in Figma and the `resolved` value to check against. `$value` is the default (light) mode so the file still reads as DTCG.
The CSS alias layer is **excluded** from the export: 118 Semantic variables, not 162. In Figma there is one variable per canonical token; a second variable aliasing it would be a duplicate maintained by hand, which is exactly what the alias layer exists to avoid in code.
Consequence: mode names match `attribute` in `tokens/themes.config.ts` (`light`, `dark`, `hc-light`, `hc-dark`, `linen`, `linen-dark`), so a Figma mode maps 1:1 to `data-iz-theme`. Still unverified against a real Figma import — `docs/figma/PHASE-1-FIGMA.md` stays `pending` until a file exists and its node IDs are in the manifest.

## ADR-016 — `dist/` is generated and never committed; the build order is vite first, tokens second
Problem: two generators write into the same directory. `vite build` empties `dist/` before it writes `index.js`, `styles.css` and the `.d.ts` files, while `tokens:build` writes `dist/design-tokens.css`, `dist/css/<theme>.css`, `dist/ts/tokens.d.ts` and `dist/figma/tokens.json`. Running them in the wrong order silently deletes the token outputs — `npm run build` did exactly that, and nothing noticed.
Decision: `dist/` stays in `.gitignore` — it is not committed, reviewed or diffed (2026-10-23 review call). `npm run build` is `vite build && npm run build:tokens && node scripts/check-package.mjs`, in that order, because vite is the one that empties the directory.
The committed generated files stay committed: `src/styles/design-tokens.css`, `src/styles/tokens.d.ts` and `docs/specs/tokens.dtcg.json`. They are what Storybook, `check:specs` and the future MCP server read without a build step. `dist/` is only the tarball, so a consumer or CI runs `npm run build` first.
`scripts/check-package.mjs` asserts that every path `package.json` promises exists after the build. It immediately found one that never did: `exports["./tokens.css"]` pointed at `./dist/design-tokens.css`, which no generator wrote — `import '@iz/design-system/tokens.css'` would have failed for every consumer. `tokens:build` now writes that file, and two useful exports were added: `./css/*` (one theme on its own, e.g. `@iz/design-system/css/linen.css`) and `./figma.json`.
Consequence: a renamed or moved output fails the build instead of shipping a broken tarball.

## ADR-017 — The library names typefaces; the consumer loads them
Problem: `specs/HANDOFF.md` specifies Space Grotesk, IBM Plex Mono and Archivo (wdth 112) for linen, and Inter for the base theme. Phase 1 created the `font.family.*` tokens but nothing loaded a single face, so every linen review was looking at the fallback stack — the typography was specified and invisible.
Options: (a) vendor the `.woff2` files into the repo and ship `@font-face` from the library; (b) declare `@font-face` in the library pointing at paths the consumer provides; (c) name the faces in tokens, document the loading contract, and let the consumer load them.
Decision: (c). All three faces are OFL, so (a) is legally fine — but a library that ships fonts takes over decisions that belong to the app: subsetting, self-hosting vs CDN, `font-display`, preload order, and the app's Content-Security-Policy. It also doubles the tarball for consumers who already load Inter. (b) is the worst of both: a hard dependency on a path the library cannot verify.
Consequence: `docs/TOKENS.md § Fonts` is the contract — which face, which weights, which axis, per theme. Storybook loads all four from Google Fonts in `.storybook/preview-head.html` so a design review sees the real typefaces; that file is Storybook-only and ships with nothing.
Known gap, parked: a variable font renders at its default width unless the element sets `font-variation-settings: 'wdth' 112`, and figures need `font-variant-numeric: tabular-nums`. DTCG has no axis type, so neither is a token yet; the first component to use the display or figure role sets both in CSS.

## ADR-018 — The Figma mirror is imported by a plugin, not typed in
Problem: ADR-004 makes Git canonical and Figma a mirror that has to be re-entered. With six themes that mirror is 271 variables and 696 per-mode alias assignments. Typed by hand that is hours of work, it has to be redone after every token change, and a wrong alias is invisible — the variable shows a plausible colour in the mode you are looking at and the wrong one in the other five.
Options: (a) type them in, following `docs/figma/PHASE-1-FIGMA.md`; (b) the Figma Variables REST API, which needs a personal access token with file-write scope; (c) a development plugin that reads `dist/figma/tokens.json` from the user's own disk.
Decision: (c), `tools/figma-plugin/`. `networkAccess: none` — the file is chosen locally and nothing is transmitted, so no token and no credential handling. (b) was rejected because it puts a long-lived write-scoped token into the loop for a job that runs a handful of times.
The plugin is idempotent: variables are matched by name, values and aliases updated, nothing duplicated. That makes "re-run the plugin" the answer to the manual-step problem in ADR-004 — the Figma side of a token change goes from an hour of re-entry to one click.
Scope, deliberately: variables only. Easing (`cubicBezier`, 6 tokens) has no Figma variable type; shadows and composite text styles are effect/text styles, not variables; and the Button component set stays manual, because a component is a design decision, not a data transform.
Verification without Figma: `code.js` was run against a mock Plugin API and the real `dist/figma/tokens.json` — 155 Primitives + 116 Semantic variables, 696 alias assignments (116 × 6), **0 raw values and 0 unset modes**, 6 expected skips. The zero-raw count is the meaningful one: it proves every semantic value in every mode found a real primitive to point at. Still unverified inside Figma itself; `docs/figma/PHASE-1-FIGMA.md` stays `pending` until a file exists.

## ADR-019 — The Figma importer degrades on plan limits instead of failing
Problem: Figma variable **modes** are a paid feature — Starter has none, Professional allows 10 per collection, Organization 20 ([Figma plans and features](https://help.figma.com/hc/en-us/articles/360040328273-Figma-plans-and-features)). The six modes this system needs fit Professional, but the first run was attempted on a Starter team, where `collection.addMode()` throws. The plugin would have created 155 Primitives, then failed partway through Semantic, leaving a half-built file and an exception for a message.
Decision: `syncModes` catches the refusal per mode, imports every mode the plan allows, and reports the ones Figma refused with what to do about them. Because the plugin is idempotent, re-running after an upgrade fills the missing modes in place — there is nothing to undo first.
Consequence: on Starter the file still gets all 271 variables, correctly aliased, in one `light` mode. That is a real artefact — just not the theming proof, which needs more than one mode by definition. The report says so rather than implying success.
Verified both paths against the mock Plugin API: with modes allowed, 116 × 6 = 696 aliases; with `addMode` throwing, 116 aliases in one mode, 5 modes named as refused, 0 raw values and 0 unset in both.
This is the general shape the system should prefer: a tool that hits someone else's limit reports the limit, keeps what it could do, and stays safe to re-run.

## ADR-020 — The Figma plugin carries its own data; the file picker is the fallback
Problem: the first two real runs of the importer failed on the human step, not the code — once by pressing *Import from manifest* and expecting it to run, once by picking `docs/specs/tokens.dtcg.json` instead of `dist/figma/tokens.json`. Both files are generated, both are named `tokens`, and a file dialog inside a plugin iframe is the least forgiving UI in the whole workflow. Every remaining failure mode lived in "pick the right file".
Decision: `tokens:build` prepends the current `dist/figma/tokens.json` to the plugin as a constant (`IZ_TOKENS`, plus `IZ_TOKENS_BUILT_AT`), writing `tools/figma-plugin/code.js` from `src/code.js` and copying `src/ui.html`. The generated pair is gitignored; the manifest points at it. Running the plugin is now: open it, press Import. The file picker stays underneath for importing a different `tokens.json` (another branch) without a rebuild, and a picked file wins over the baked copy.
Consequence: Figma re-reads a development plugin's files on every run, so after a token change the loop is `npm run build` → run plugin — no re-import, no dialog. The plugin reports the build time so a stale bake is visible. `code.js` is 250 KB with the data inlined, which is fine for a development plugin and irrelevant to the library tarball (`tools/` is not in `files`).
Verified against the mock Plugin API in all four paths — baked (696 aliases), picked file (696), wrong file (refused by name), Starter plan (116 aliases, 5 modes reported refused) — with 0 raw and 0 unset values in every path that imports.
The general lesson, worth more than the plugin: when a step keeps failing on the human, move the decision out of the human's hands at build time rather than writing a better instruction.

## ADR-021 — Desktop control height is 40 px: `size.target.lg`, and Button `md` moves from 32 to 40
Problem: the scaffold's Button sizes were 24 / 32 / 44 (`size.target.min | md | touch`). `specs/HANDOFF.md` specifies 40 px desktop / 44 px phone for both buttons and inputs. Writing TextField at 40 next to a Button at 32 would put a field and its button in the same quick-add row at different heights — the first pattern would have shipped with the inconsistency baked in.
Options: (a) raise Button `md` to 40 and share the token with TextField; (b) keep Button at 32 and accept taller fields; (c) give Button a fourth size.
Decision: (a), 2026-10-25. New semantic token `size.target.lg` = `{size.10}` (40 px). The scale is now `min` 24 (WCAG 2.5.8 floor) · `md` 32 · `lg` 40 (desktop control) · `touch` 44. Button maps sm → `min`, md → `lg`, lg → `touch`; TextField md → `lg`, lg → `touch`. The token is named for the target scale, not for a component's size prop, which is why Button `md` reads `size.target.lg` — the mapping is one comment in each CSS file.
Reason: the handoff is the consumer and nothing was built on 32 yet; aligning once now is cheaper than carrying a mismatch into nine patterns. `size.target.md` (32) stays — Chip-adjacent controls and dense desktop tables may want it — but nothing uses it today.
Consequence: Button's story label and e2e assertion move to "Medium 40px" / 40; Figma's Button component set binds height to `size/target/lg`; the Figma mirror gains one variable, so the plugin is re-run after the next build. Rejected: (b) — visibly broken rows; (c) — breaks the sm/md/lg vocabulary in `UBIQUITOUS-LANGUAGE.md`.

## ADR-022 — Inputs use React Aria's `validationBehavior="aria"`, not the default `"native"`
Problem: React Aria's default for text fields is native constraint validation: `isRequired` becomes the `required` attribute, the browser shows its own validation bubble on submit, and the empty `errorMessage` slot is not rendered until the browser reports an error. TextField's unit test for "the error element exists before it is shown" failed for exactly that reason, and the spec's rule that the browser bubble must never compete with `errorMessage` was being violated silently.
Decision: every Inputs component sets `validationBehavior="aria"`. `isInvalid` is fully controlled by the form or pattern (so one rule runs on submit and on server response alike), `isRequired` emits `aria-required`, `aria-invalid` + `aria-describedby` carry the error, and the error element is always in the DOM — empty while valid.
Consequence: the computed accessible description carries a trailing space while valid (an empty referenced element); assistive tech collapses whitespace, so tests match a regex. Native form submission still works; only the browser's *validation UI* is out of the loop. Rejected: keeping native mode and rendering our own error on top — two sources of truth for the same state.

## ADR-023 — Checkbox wires its own label association on top of React Aria's `CheckboxField`
Problem: the composition that keeps description and error *out of* the accessible name is `CheckboxField` (div) + `CheckboxButton` (label around the hidden input) + `Label` + `Text` slots. In React Aria Components 1.22.1, `CheckboxField` provides the `Text` slots and validation context but **no `LabelContext`**: a `<Label>` inside it renders as plain text, the input gets no `id` and no `aria-labelledby`, and the checkbox has an empty name. Every story failed axe's `label` rule and the unit test could not find the control by name — the first time a React Aria composition did not do the a11y wiring for us.
Options: (a) the classic `<Checkbox>` (one `<label>` root) with description and error inside it — the help text then becomes part of the name ("I agree to the terms We store the lead only…"); (b) `CheckboxField` with the association wired by hand; (c) wait for an upstream fix.
Decision: (b). `useId()` twice: the input gets `id`, the label gets `id` + `htmlFor`, and `aria-labelledby` is passed when a visible label exists (`aria-label` from props wins when it does not). Clicking the label text toggles through the native `htmlFor`, and the name is exactly the label text. The unit test "takes its name from the visible label, and clicking the text toggles it" is the guard: if a future React Aria release wires this itself, the double wiring is harmless; if it changes shape, the test says so.
Consequence: the same pattern applies to any future control built on a `*Field` wrapper (Switch, RadioGroup items) — check the name first, then trust the library. Rejected: (a) — pollutes the name and reads the help text on every focus; (c) — blocks the component on someone else's roadmap.

## ADR-024 — A 28 px compact target (`size.target.sm`) and a 12 px `font.caption` role, for Chip
Problem: `specs/HANDOFF.md` specifies chips at 28 px with 12 px text. The target scale had 24 / 32 / 40 / 44 and the only 12 px type role was `font.code` (a mono role for `<kbd>` and code). Chip would otherwise have to reach for a primitive directly — forbidden by the tier rule — or misuse `font.code.size` for a sans label.
Decision: primitive `size.7` = 28 px; semantic `size.target.sm` = `{size.7}`, so the scale reads `min` 24 · `sm` 28 · `md` 32 · `lg` 40 · `touch` 44. Semantic `font.caption.{family,size,line-height,weight}` = sans / 12 px / 1.3333 (12/16) / medium, with linen overriding the face to Space Grotesk exactly as body, label and heading do.
Why 28 is allowed: WCAG 2.5.8 AA is 24 × 24; 44 is our recommended touch target, never the minimum (ADR-005). A 28 px chip in a row of chips relies on the *spacing* exception — the pattern owns the gaps — and the spec says so in `a11y.targetSize`.
Consequence: the Figma mirror gains three variables (`size/target/sm`, `font/caption/*`) and one linen mode value; re-run the plugin after the next build. Rejected: using `size.target.min` (24) and padding the chip to 28 by hand — a hidden number in CSS that no token documents.

## ADR-025 — One `Chip`; the variant decides the element; `Tag` is retired as a name
Problem: `docs/UBIQUITOUS-LANGUAGE.md` named two components — *Tag (static)* and *Chip (removable, interactive)* — while `specs/HANDOFF.md`, the consumer, calls property (static), stage (static or cycling) and filter (toggle) pills all "Chip" and has no removable item anywhere. Two names for one 28 px pill would have made every pattern author choose, and the only real difference between the kinds is the ARIA role.
Options: (a) one `Chip` with `variant: property | stage | filter`, where the variant decides `<span>` vs `<button>`; (b) `Tag` + `Chip` as two components sharing CSS; (c) one `Chip` now and keep the vocabulary line as "reserved".
Decision: (a), 2026-10-26 review call. property and stage render a `<span>` with no role; filter renders React Aria's `ToggleButton` (`aria-pressed`); a stage with `onPress` renders a `Button`. The discriminated union makes `onChange` on a stage or `onPress` on a filter a type error, so the element is never ambiguous at the call site. `Tag`, `Pill` and `Label` are now listed as names not to use.
A second vocabulary change rode along: `emphasis: quiet | tint | strong` — visual weight with no semantic meaning. The handoff's stage colouring (every stage quiet, Interview tinted, Offer solid) is weight, not status, and the product rule is one accent per screen; `tone` would have invited status colours onto chips. The stage → emphasis mapping belongs to the StageChip pattern.
Consequence: one CSS module, one Figma component set with `Variant` and `Emphasis` properties, one spec. Selected is never colour-only (inverse colours + `font.caption.weight-strong` + `aria-pressed`). Rejected: (b) — doubles the cycle for no consumer; (c) — lets the vocabulary and the code drift until someone trips on it.

## ADR-026 — `radius.xl` = 14 px, so the triage card has a canonical token
Problem: `specs/HANDOFF.md` gives cards radius 400 (12 px) and the triage card radius 500 (14 px). 12 is `radius.lg`; 14 existed only as the alias-layer name `radius.500` → primitive `radius-scale.3-5`, and the alias layer is a compatibility surface, not a vocabulary (ADR-009). Card's `radius` prop needed a canonical name to point at.
Decision: semantic `radius.xl` = `{radius-scale.3-5}`. The scale reads `sm` 4 · `md` 8 · `lg` 12 · `xl` 14 · `full`. The alias `radius.500` keeps working and resolves to the same primitive.
Consequence: Card exposes `radius: 'lg' | 'xl'`; TriageCard passes `xl`. One more Figma variable after the next build. Rejected: letting TriageCard override `--iz-card-radius` with the alias name — a component-token override is an escape hatch, not the way a documented size should be reached.

## ADR-027 — `shadow.overlay` enters the pipeline: alpha colours and the DTCG shadow composite
Problem: `specs/HANDOFF.md` § Elevation gives one shadow — `0 8px 24px rgb(0 0 0 / 0.18)` on popovers and the toast, dropped in dark mode — and Toast is its first consumer. The pipeline could not express it: colours had no alpha, `toCss` had no `shadow` case, the validator had no `shadow` shape, and the "a semantic token aliases a primitive" rule would reject a composite object outright.
Decision: colours accept an optional `alpha` (0–1) and emit `rgb(r g b / a)` when translucent; `shadow` is the DTCG composite `{color, offsetX, offsetY, blur, spread}` whose **every part is an alias** to a primitive — the validator requires that, which is why the composite is exempt from the raw-value rule: it holds no raw value, only references. `toCss(shadow)` resolves the parts through the same alias chain as everything else, so a theme can re-point any part. Primitives: `color.overlay-shadow` (black, α 0.18) and `color.transparent` (α 0). Semantic: `shadow.overlay` = 0 / 8 / 24 / 0 with the overlay ink; `dark`, `hc-dark` and `linen.dark` override it to a transparent, zero-size shadow — DTCG has no "none", and a shadow that is there-but-invisible is both honest and representable.
Consequence: Cards still carry no shadow (ADR, Card spec); only Popover, Toast and the palette consume `shadow.overlay`. Figma has no variable type for a shadow, so the plugin reports it as skipped and it becomes an *effect style* by hand; the plugin now honours colour alpha so the overlay ink imports as translucent rather than opaque black. Rejected: a `string`-typed token holding the CSS literal — it would bypass every rule the system has.

## ADR-028 — Toast is built on React Aria hooks, not on `UNSTABLE_Toast`
Problem: React Aria Components 1.22.1 ships Toast as `UNSTABLE_ToastRegion` / `UNSTABLE_Toast` over react-stately's `ToastQueue`. Its model is a landmark region whose toasts are `role="alertdialog"` (with an inner `role="alert"`), focusable, queued FIFO under `maxVisibleToasts`. The handoff and `docs/ACCESSIBILITY.md` ask for the opposite temperament: a single `aria-live="polite"` region with `role="status"`, never stealing focus, **one at a time with the new one replacing the old**, 6 s with pause on hover/focus.
Options: (a) `UNSTABLE_Toast` and fight it — override the role, close every visible toast before `add` to fake replacement, accept an API marked unstable; (b) our own small component on the hooks that do carry weight (`useHover`, `useFocusWithin`, `Button` for the action), with a `role="region"` landmark wrapper so landmark navigation still reaches it; (c) wait for the stable release.
Decision: (b). The behaviour the handoff specifies is ~80 lines and entirely about timing and roles; the library's value here is in the parts we keep (hover, focus-within, the Button). Rejected: (a) — an `alertdialog` that we rename to `status` is still announced and focused like an alert dialog by some AT, and "close everything then add" is a workaround for a queue we do not want; (c) — Toast is on the critical path for Today (Done + Undo).
Consequence: when the API stabilises, swapping to it is a contained change behind the same `ToastProps`; the spec's keyboard map and roles are the contract either way.

## ADR-029 — The menu popover stays modal: Tab is contained, `isNonModal` is not used
Problem: `docs/ACCESSIBILITY.md` said "Popover (non-modal): … Tab out closes", and Menu's first spec and e2e repeated it. In a real browser the e2e failed: with the menu open, Tab and Shift+Tab do nothing — focus stays on the current item, the menu stays open. A browser probe confirmed it. React Aria's `Popover` is modal by default: while open, the rest of the page is hidden from assistive technology and focus is contained; the only thing the library offers against that is `isNonModal`, whose own documentation says it "may negatively impact the screen reader experience" and should be used only by components designed for it, such as ComboBox.
Options: (a) set `isNonModal` to get Tab-out-closes and match the old rule; (b) keep the modal popover and make the rule, spec and tests say what the component does; (c) intercept Tab ourselves and close.
Decision: (b). APG's Menu Button pattern defines arrows, Home/End, type-ahead, Enter/Space and Escape — not Tab — and the exits a menu needs (Escape, a choice, click outside, all returning focus to the trigger) are present and documented. WCAG 2.1.2 permits contained focus when the exit is standard and documented; here it is Escape, in the keyboard map. `ACCESSIBILITY.md` now distinguishes the non-modal popover (ComboBox listbox) from the modal one (Menu).
Rejected: (a) — trades an invisible AT regression for a visible keyboard convenience; (c) — re-implements overlay focus management against the library and would have to be kept correct across releases.
Consequence: the `Tab` row in `Menu.spec.json` says "no effect while open"; the e2e asserts exactly that; the story's Keyboard play presses Tab and expects nothing to move. This is the first time a repo rule, not my assertion, had to change — and the e2e that failed is the reason it did.

## ADR-030 — `color.backdrop`: one translucent scrim behind a Modal
Problem: Modal needs a backdrop and the system had no token for it; the handoff specifies no scrim value.
Decision: primitive `color.scrim` = black at α 0.4; semantic `color.backdrop` = `{color.scrim}`, the same in every theme. Translucent, not opaque: the page stays visible so the user keeps their place, and the dialog's own surface (`color.surface.overlay` + `shadow.overlay`) carries the separation. Nothing is ever written on the scrim, so it has no `fg.on-*` partner and `check:contrast` does not treat it as a background role.
Consequence: dark themes may later want a stronger scrim (the dialog is a lighter surface on a dark page, so α 0.4 reads softer); if so, override `color.backdrop` in the dark theme files — the component has no theme code. The Figma mirror gets `color/scrim` as a translucent colour (the plugin honours alpha).

## ADR-031 — Switch is a setting, not a form field: no validation props, Space only
Problem: Switch and Checkbox look like siblings (both are React Aria toggles on a hidden native input, both get the ADR-023 label wiring), so the obvious move is to copy Checkbox's prop surface — isInvalid, isRequired, errorMessage, isIndeterminate. `docs/ACCESSIBILITY.md` also listed `Enter` as a toggle key for Switch.
Options: (a) copy Checkbox's props for symmetry; (b) a Switch that applies the setting on change and exposes only what a setting can be — on/off, disabled, read-only, described; (c) one `Toggle` component with a `kind` prop.
Decision: (b). A switch applies immediately (WCAG 3.2.2 — the change *is* the expected result), so nothing is submitted, nothing can be 'required' or 'invalid', and a required on/off is consent, which is a Checkbox in a form. No indeterminate: two states. `Enter` is corrected to 'does nothing' — React Aria's switch is a native input, and Enter belongs to the surrounding form exactly as the Checkbox spec already says; the ACCESSIBILITY.md line was wrong, not the component. (a) rejected: props that can never be true are a lie in the type; (c) rejected: the two differ in meaning, not in a flag.
Consequence: a reviewer who sees `isRequired` on a Switch in app code has found a Checkbox. `labelPlacement="start"` covers the settings-list layout (text left, switch at the row's end) without changing DOM order or name.

## ADR-032 — `agent/llms.txt` is generated from the specs, committed, and freshness-checked in CI
Problem: Phase 2's definition of done (specs/HANDOFF.md) says `agent/llms.txt` lists every primitive. A hand-written llms.txt drifts the day a component is added or a summary changes; one generated only at build time is invisible on GitHub, where an agent without the package is most likely to read it.
Options: (a) hand-written, edited per component; (b) generated at `npm run build` only, not committed; (c) generated from `docs/specs/*.spec.json` by `scripts/gen-llms-txt.mjs`, committed, with `npm run check:llms` failing CI when the committed file is stale.
Decision: (c), the same model as the token output. The specs are already the enforced source of truth (check:specs), so the file carries their summary, role, status and import line per component, the token policy, the theme list, and links to the documents an agent must read before changing anything. Deterministic output — no timestamps — so the check is exact. `npm run build` regenerates it, because `agent/` ships in the package.
Rejected: (a) drifts; (b) invisible where it is needed most. The MCP server from the same specs stays in Phase 4 (docs/ROADMAP.md).
Consequence: adding a component updates llms.txt by running `npm run check` (which runs gen via check:llms only in check mode — run `npm run gen:llms` after a new spec and commit the result; CI tells you if you forgot).

## ADR-033 — Patterns live in the package under `src/patterns/<product>/`, specified like components; the row owns no shortcuts, no toast, no `focused` prop
Problem: Phase 3 begins with ActionRow, the first of the nine Job Search HQ patterns. Three questions: where do product patterns live, are they held to the component cycle, and how much of the handoff's ActionRow (J/K/D/S/O keys, `focused` prop, done toast + live region) belongs to the row itself.
Options: (a) patterns in the app repo only; (b) patterns in this package under `src/patterns/jobsearch/`, category `Pattern`, same spec → stories → tests → e2e → MDX → manifest cycle, checked by `check:specs` and listed in llms.txt; (c) a separate `@iz/patterns` package.
Decision: (b), as specs/HANDOFF.md lays out (`src/patterns/jobsearch/*`, "every pattern composes primitives", MCP `get_spec` for each). Same lint, same token rules, same gates. And three deviations from the handoff's ActionRow sketch, each for an a11y reason: (1) the letter shortcuts J/K/D/S/O are the *list's* (Today) — a keydown listener on a row fires inside quick-add's input when focus is within it, and the list already knows the current row; the row exposes `onDone` / `onSnooze` / `onOpen` and stable accessible names instead. (2) `focused` is not a prop: the row outline is `:focus-within`, because focus is a browser state (ROADMAP rule). (3) The Undo toast and the "Done. 3 due today." live region are the list's: the Toast spec allows one toast per app and one announcement per change. The row animates the done moment and nothing more.
Rejected: (a) loses the spec, the tests and the llms.txt entry — exactly what the case study shows; (c) is a second package for nine files.
Consequence: `check:specs` globs `src/patterns/**` and accepts category `Pattern`; `gen-llms-txt` lists patterns in their own section. One more deviation surfaced in code: the handoff's hover of `bg-sunken at 40%` is a colour without a token, and stylelint forbids `color-mix` on purpose (ADR-027) — the row hovers in opaque `color.surface.sunken`; an alpha token can follow if linen needs it (PARKING.md). The Today list (Phase 4) is where the keyboard model, the groups and the toast are built; ActionRow must stay usable without any of them.

## ADR-034 — StageChip: keys on the button, Offer is final, the flip is the in-half only
Problem: the handoff's StageChip cycles with click or Shift+→/←, flips 240 ms on the Y axis (old label out 0→90°, new label in 90→0°), and the Chip spec said the pattern "binds the keys on the row". Three choices: where the keys live, what happens at the ends of the cycle, and how to animate a controlled label change without delaying the state.
Options: keys (a) on the row / document, (b) on the chip's own button via a new `onKeyDown` passthrough on Chip's cycling stage; ends (c) wrap Offer → Lead, (d) Offer is final and Lead has no previous; flip (e) defer `onChange` until the out-animation ends and then play the in-animation, (f) fire `onChange` at once and play only the in-half by remounting the label (`key={stage}`).
Decision: (b), (d), (f). Keys on the button work wherever the chip is rendered and cannot fire inside an input (the same reason ADR-033 keeps letters off the row); Chip gains one prop, documented in its spec. Offer is final because a wrap is the one stage change a user could make by accident, and Lead has nothing before it. The in-half flip keeps the app's state change immediate (backlog #10: apply, then Undo) and needs no `animationend` bookkeeping; under reduced motion the duration token is 0 and the label swaps. The mapping stage → emphasis moves out of ActionRow into StageChip as the exported `stageEmphasis`; Rejected and Withdrawn are quiet and static (backlog 0c).
Rejected: (a) a row/document listener; (c) wrapping; (e) a deferred state change — a 120 ms gap between press and truth, and a zero-duration `animationend` that browsers do not reliably fire.
Consequence: the out-half of the handoff's flip is not played; if it is missed in use, the honest fix is a two-label crossfade, not a deferred `onChange`.

## ADR-035 — WeeklyGoal: `role="meter"`, the spring is a keyframe, `duration.moment` is a token, the figure font is a component rule
Problem: the handoff's WeeklyGoal is `role="img"` with a full sentence, animates the goal-met moment with a spring (stiffness 260 / damping 18) over 700 ms, and PARKING held two open questions from Phase 1: how to tokenise a spring (DTCG has no type for it) and how to set the figure face's width axis and tabular numerals (no axis type either). The repo has no motion library.
Options: role (a) `img` as sketched, (b) `meter` with `aria-valuenow/min/max` and `aria-valuetext` carrying the sentence; spring (c) add Motion and export a spring config, (d) a CSS keyframe that overshoots to 1.12 and settles, on a `duration.moment` token aliasing the existing 700 ms primitive; figure face (e) a `$extensions` block, (f) a documented component rule in CSS (`font-variation-settings: "wdth" 112`, `font-variant-numeric: tabular-nums`).
Decision: (b), (d), (f). A gauge is a quantity in a range — `meter` tells a screen reader exactly that and lets the value change be announced as a value, not a re-read sentence; the sentence stays as `aria-valuetext`. The spring as a keyframe needs no dependency, zeroes under reduced motion through the token like every other transition, and the only observable difference from a physical spring is in the middle 300 ms of a once-a-week moment. `duration.moment` (700) is the one new semantic token; the five signature events the handoff names are its only consumers. The figure rule lives in the pattern's CSS with a comment, as PARKING proposed; WeeklyGoal is the first consumer.
Deviations from the handoff kept small and named: the footer's live text changes when the state does (not at the end of the animation — that would need a timer bound to a token); StreakBar and the adjust prompt are backlog #12 (P1) and a later pattern, so `history` and `onAdjustTarget` are not props yet.
Rejected: (a) re-reads the whole sentence on every change; (c) a dependency for one moment; (e) an extension no tool reads.
Consequence: one new variable for Figma (`duration/moment`); `check:contrast` unaffected. If a real spring is ever wanted, it replaces the keyframe, not the token.
